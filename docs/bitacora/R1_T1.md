# R1 · T1 Backend · bitácora

## Hecho
1. **BD y migraciones** (`server/db/`): SQLite `node:sqlite`, WAL + synchronous NORMAL, migraciones por `PRAGMA user_version`. Esquema de `docs/MODELO_DATOS.md` + `sesiones_admin` + `salas.token_tablero`. `npm run seed`: superadmin idempotente desde `SUPERADMIN_USUARIO`/`SUPERADMIN_CLAVE` y `--sala "X" --mesas N` crea sala desde la plantilla `foodsume_2026` (proyectos, hojas, contenido, token del tablero). El servidor también asegura el superadmin al arrancar.
2. **API participante** (`server/rutas/api.ts`, `server/dominio/participantes.ts`): mesa por código, inscripción con consentimiento (versión, sha256 del texto, `politica_url`, IP, UA), perfil balanceado, `GET /api/yo`, `PUT /api/votos` (upsert, 1/3/5/7/9, 6 obligatorias), `GET /api/resultados` con `alcance_resultados`, `vista_participante` y precierre.
3. **Máquina de estados** (`server/dominio/estados.ts`): acciones con 409 `TRANSICION_INVALIDA`, todo a `eventos`.
4. **Precierre** derivado por mesa y sala (solo avisa, `preliminar: true`, evento `precierre` con mensaje). `abrir_ronda_2` → `revelar_hojas = true`. **Cierres programados**: chequeo perezoso en cada petición `/api/*` + intervalo de 15 s; eventos `por: "programado"`.
5. **Tablero** `GET /api/tablero/{salaId}` (id o código) con alcance sala/mesa, promedios, distribución, n_votos, t2m/x/y por ronda, progreso por mesa, ETag → 304.
6. **Admin**: login scrypt, cookie `hz_admin`, roles, gestión de admins solo superadmin (403 `SOLO_SUPERADMIN`), cambio de clave obligatorio (403 `CAMBIO_CLAVE_REQUERIDO`), CRUD, PATCH config, reasignar participante, QR SVG (`qrcode`), export CSV con BOM y `;` (con protección contra inyección de fórmulas).
7. **Pruebas** (160 en verde): golden del motor, integración de cada endpoint (`tests/server/admin.test.ts`, `participante.test.ts`), precierre y cierres programados con reloj simulado (`flujo.test.ts`), e2e sintético 20 personas × 2 rondas por API contra el golden (`e2e_sintetico.test.ts`).
- Extra: cliente compartido `web/shared/api/` (tipos del contrato + `api.*` con ETag y token), simulador de carga `npm run simular` (40 personas, 4 mesas, polling 2,5 s: p95 en servidor ≈ 31 ms, puntos verificados de forma independiente, 0 errores).

## Verificación de aceptación
- e2e sintético pasa: `tests/server/e2e_sintetico.test.ts` ✓
- Sala nueva recorrida completa por API (inscripción → R1 → precierre → cierre → R2 → cierre → sala cerrada): mismo e2e ✓
- Cierre programado con reloj simulado (perezoso e intervalo): `tests/server/flujo.test.ts` ✓
- Admin normal → 403 en `/api/admin/admins` (GET/POST/PATCH): `tests/server/admin.test.ts` ✓
- No existe forma de convertir un participante en admin: tablas y sesiones separadas, rol `admin` forzado al crear, token de participante no sirve como sesión admin (pruebas en `admin.test.ts`) ✓

## Para las otras terminales
- API real: `npm run dev:api`. Crea datos con `SUPERADMIN_USUARIO=paola SUPERADMIN_CLAVE=... npm run seed -- --sala "Ensayo" --mesas 4` (imprime URLs de mesas y tablero).
- Cambios aditivos al contrato: ver `docs/DECISIONES.md` (prefijo `CONTRATO:`). Ojo: ids de proyecto vienen de la semilla (`crypto_trade` con guion bajo; el mock decía `crypto-trade`).
- `url_tablero` = `/tablero/{salaId}?mesa={mesaId}&t={token}`; la API acepta también el código de sala.
